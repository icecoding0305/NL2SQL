> 面向:企业内部风险/数据分析场景。文档是 README 的补充,重点讲"系统怎么被组织"与"一次查询怎么流动"。

## 1. 系统架构总览

NL2SQL 是一个基于 **LangGraph 状态图**的自然语言 → SQL 智能体服务。核心由三块组成:

```
┌─────────────────────────────────────────────────────────────────────┐
│                        前端(React + TS + antd)                       │
│  数据问答 · 表与注释 · 审批队列 · 历史审计 · 配置管理                   │
│          │ WebSocket 流式事件 / REST                                  │
└──────────┼──────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│                      FastAPI 服务(main.py + api.py)                  │
│  - /api/ws/query   查询流式执行线程 + EventStream 桥接                │
│  - /api/*          查询/审批/恢复/历史/审计/反馈/配置/表结构           │
│  - SQLite checkpoint (LangGraph 中断状态持久化)                       │
└──────────┬──────────────────────────────────────────────────────────┘
           ▼
┌─────────────────────────────────────────────────────────────────────┐
│              LangGraph 状态机(11 个功能模块 + 3.5 澄清路由)           │
│  entry → query_resolution → schema_retrieval → 3.5 → plan_generation │
│    └ simple → SQL → 静态校验 → 敏感 → 执行 → 解释                     │
│    └ complex → 计划生成 → 计划校验(回路) → SQL ...                   │
└───────┬──────────────┬──────────────────────────────┬───────────────┘
        │              │                              │
        ▼              ▼                              ▼
┌───────────────┐ ┌────────────────┐          ┌──────────────────────┐
│ LLM 层        │ │ 数据层          │          │ 元数据 / 检索层       │
│ 主模型(计划/  │ │ MySQL / Postgres│          │ M-Schema(事实源)      │
│ 解释)         │ │ 只读执行器      │          │ SchemaCatalog(投影)   │
│ SQL 专用模型  │ │ pragma 只读事务 │          │ Embedding + 向量库     │
│ 千问等        │ │ EXPLAIN/LIMIT   │          │ memory / pgvector     │
└───────────────┘ └────────────────┘          └──────────────────────┘
```

### 1.1 分层职责

| 层 | 组件 | 职责 |
| --- | --- | --- |
| **接入层** | `main.py` / `api.py` | HTTP + WebSocket API、事件流桥接、审批/恢复、历史/反馈/配置 |
| **编排层** | `graph.py` + `nodes/` | 11 个功能模块的状态图、两条重试回路、interrupt 人工确认 |
| **状态层** | `state.py` | Pydantic v2 强类型状态(含 QueryIntent / SchemaPlan / QueryPlan) |
| **元数据层** | `schema_ingest/` | 数据库 → M-Schema → SchemaCatalog 投影 → 向量索引 |
| **检索层** | `schema_planner` + `term_mapping` + `vector_store` | 意图解析 → 锚点/实体/桥接表规划 + 术语精确命中 + 向量召回 |
| **LLM 层** | `llm.py` | 多 provider、按节点分配主模型/SQL 模型/离线模型 |
| **执行层** | `executor.py` | MySQL/Postgres 只读执行、EXPLAIN 守门、强制 LIMIT |
| **安全层** | `sql_dialect` + m8 + m9 | AST 校验、字段幻觉拦截、行级过滤、风险三态决策 |

## 2. 核心数据流:从数据库到可检索

```
数据库 INFORMATION_SCHEMA
   │ ingest_schema.py(全量/增量)
   ▼
raw M-Schema ──► profiler 字段画像/分类
   │             └─ table 级/column 级 embedding 文本
   ▼
候选描述(LLM 分阶段生成) ──► 人工审核(review_schema_comments.py)
   │                           └─ 通过 → override 层(不改 DDL)
   ▼
effective M-Schema(完整事实源)
   │  ├──► schema_catalog.yaml(运行时精简视图,带 _meta.semantic_hash 溯源)
   │  └──► 表级 / 字段级 / 关系级向量索引(memory 或 pgvector)
   ▼
模块 3 检索:QueryIntent + SchemaPlan + 术语 + 向量
```

关键不变量:
- **M-Schema 是唯一事实源**。SchemaCatalog 和向量索引都是它的派生视图,带 `semantic_hash`
  校验同步,不需要手修。
- **表间关系**来自数据库外键(M-Schema `relations`),用于 SchemaPlan 的桥接补表和 SQL 的合法 JOIN。
- **注释补全写在 override 层**(`schema_metadata_override`),不修改数据库 DDL。

## 3. 一次查询的完整流程(端到端)

```
用户问题 + user_id + data_scope(=系统,如 risk_mart)
  │
  ▼ M1 入口
校验身份与权限 → 写入 state(下游只读)
  │
  ▼ M2 时间范围澄清
仅当问题表现出时间意图但缺明确范围时拦截;否则放行
  │
  ▼ M3 Schema 检索
  a) 解析 QueryIntent:度量 / 过滤 / 实体 / 属性 / 分组槽位
  b) 术语精确命中(复合指标,强约束口径)
  c) 字段级证据打分 → 确定 锚点(核心事实)表
  d) 从 M-Schema relations 补 实体/维度 表 + 最短路径 桥接表
  e) 向量语义兜底 + 字段相关加成
  ▼ M3.5 检索置信度路由
  ├─ 同业务槽位多个高证据字段 → 字段口径澄清(interrupt)
  ├─ 证据不足 → 低置信提示(interrupt)
  └─ 高置信 / 字段明确 → 放行
  ▼ M5b 统一计划生成(所有查询均输出 QueryPlan)
      · 从检索子图构建 Query M-Schema(最小字段/关系/基数/语义绑定)
      · 兼容转换为 LogicalPlan 关系算子 DAG，并显式声明输出字段与输出粒度
  ▼ M6 计划校验(语义原子覆盖率 + 字段/关系/口径 + 输出粒度 + Join 放大风险)
     └─ 不过 → 回 M5b(上限 2 次)→ 打满降级
  ▼ (通过)
  ▼ M7 SQL 生成
      · 当前按已校验 QueryPlan 机械翻译；后续由 LogicalPlan 确定性编译为 sqlglot AST
      · 反复失败/执行报错 → 回 M7(上限 3 次)→ 打满降级
  ▼ M8 静态校验(sqlglot AST)
      · 方言合法 · 字段归属(解析别名)· 危险操作(硬失败不重试)
      · 行级过滤注入(按鉴权层 row_level_filters)
  ▼ M9 风险三态判定
  ├─ pass            → 直接执行
  ├─ approval_required → interrupt 人工确认(敏感字段/金额聚合/低置信)
  └─ hard_block      → 直接结束(如超扫描阈值)
  ▼ M10 沙箱执行(只读事务)
      · EXPLAIN 预估行数守门 · 未聚合强制 LIMIT · 超时
      · 报错 → 回 M7(上限 3 次)
  ▼ M11 结果解释
把结构化结果转自然语言摘要 + 保留原始结果表格
```

### 3.1 两条重试回路的边界(硬约束)

```
计划校验失败(M6)只在 M5b 内部打转 ──► 不退回 M3(检索)
执行报错(M10)只退回 M7(SQL 生成)────► 不退回 M5b(计划)
每种错误在离它最近的节点消化,不把整条链路从头推倒
```

## 4. Schema 检索的详细流程(schema_planner)

模块 3 是准确率的地基。普通问题走"字段驱动规划",复合术语走"精确映射":

```
用户问题
  ├─ parse_query_intent → QueryIntent(entities/measures/filters/attributes/dimensions)
  ├─ term_facts → 术语映射表中命中的复合口径(强约束)
  ▼
字段级匹配打分(按业务槽位):
  · 字段短语相似、向量相似、数据类型、语义角色、实体亲和度
  → 每个业务槽位选出候选字段集(field_candidates)
  ▼
若同一槽位多个高证据字段 → 需随机裂 澄清
  ▼
build_schema_plan → SchemaPlan:
  · anchor_tables   核心事实表(primary_fact / secondary_fact)
  · dimension_tables 实体输出/维度表(entity / dimension)
  · bridge_tables   桥接表(从 M-Schema relations 补最短路径,≤3 跳)
  · unresolved_slots + confidence
  ▼
最终 retrieved_schema = 锚点表 + 实体/维度表 + 桥接表(按权限过滤)
```

## 5. 状态模型(state.py)

```
NL2SQLState
 ├─ 查询与上下文: user_query / conversation_history / clarified_query / need_clarification
 ├─ Schema 检索:  retrieved_schema / retrieval_confidence / retrieval_candidates
 │                field_candidates / field_ambiguities / schema_plan / query_intent
 ├─ 计划:         query_plan / plan_validation_errors / plan_retry_count / max_plan_retries
 ├─ SQL:          generated_sql / used_tables / validation_errors / retry_count / max_retries / blocked_reason
 ├─ 敏感/审批:     is_sensitive / sensitive_reasons / human_approved / risk_decision
 ├─ 执行/结果:     execution_result / execution_error / final_answer
 ├─ 身份/权限:     user_id / data_scope(=系统命名空间)
 └─ 追踪:         trace_id / trace_steps / node_latencies
```

强类型子模型:`QueryIntent / SchemaPlan / PlannedTable / FieldCandidate / QueryPlan(强类型 JoinSpec/FilterSpec/MetricSpec) / IntentSlot / SchemaHit`。

## 6. 数据安全设计

| 层 | 防护 | 实现 |
| --- | --- | --- |
| 权限前置 | 系统级隔离 | `data_scope` 决定检索范围,入口注入、下游只读 |
| 执行只读 | 只读账号 + 事务 | MySQL `START TRANSACTION READ ONLY` / Postgres `READ ONLY` |
| 危险操作 | AST 硬拦截 | `DROP/DELETE/UPDATE/TRUNCATE` 等 → 硬失败,不重试 |
| 字段幻觉 | AST 交叉比对 | 引用表 ⊆ 检索集合,字段归属于真实表(解析别名) |
| 扫描上限 | EXPLAIN 守门 | 预估行数超阈值 → `hard_block` 或拒绝执行 |
| 行级过滤 | 鉴权层注入 | `row_level_filters` 独立注入,不推导自 `data_scope` |
| 敏感字段 | 风险三态 | 证件/姓名/金额聚合/低置信 → 人工确认 |
| LLM 越权 | 边界提示词 | `<USER_INPUT>` 等标记为不可信数据,禁止执行指令 |
| 脱敏 | 注释/结果 | 身份证样例打码;敏感字段从不传给 LLM 原文 |

## 7. 多轮对话与会话恢复

- **多轮上下文**:前端在会话内累积最近几轮 <问题,答案> 作为 `conversation_history`,m5b/m7
  提示词注入 `<CONVERSATION_DATA>`,追问可理解指代。
- **进度恢复**:前端 localStorage 记录活动会话;页面切换/刷新后按 `trace_id`
  从后端拉最新状态并轮询,不重复发起查询。
- **中断持久化**:SQLite checkpointer 保存 LangGraph 完整状态,服务重启后仍可恢复待审批/待澄清。

## 8. 目录结构(关键文件)

```
nl2sql_agent/
  main.py / api.py          # FastAPI 入口 + REST/WS
  graph.py                  # LangGraph 编排
  state.py                  # 强类型状态
  nodes/                    # 11 个模块 + human_review
  services/
    schema_ingest/          # 表结构入库:M-Schema / profiler / 审核 / 增量同步
    schema_planner.py       # 意图解析 + 锚点/实体/桥接规划
    vector_store/           # 向量后端(memory / pgvector)
    embedding/router.py     # 本地/API embedding
    llm.py                  # 多 provider 按节点分配
    executor.py / sql_dialect.py / term_mapping.py / checkpoint.py ...
  config/                   # 所有规则(禁止硬编码)+ prompts/
  eval/                     # 回归 + 检索基准 + 指标
  tests/                    # 87 个 pytest
scripts/                    # ingest / review / seed / dev
web/                        # React + TS + antd
data/                       # SQLite(历史/审核/快照)+ M-Schema + 向量缓存
```

## 9. 从零接入新系统(操作顺序)

```bash
# 1. 建表(可含主键/外键)
#    sql/mysql_*.sql 为转换后的建表脚本模板

# 2. 导入表结构 → M-Schema → catalog → 向量
uv run python scripts/ingest_schema.py --mode full --datasource <系统名> --business-line <系统名>

# 3. 处理待审核注释(缺注释的表)
uv run python scripts/review_schema_comments.py list
uv run python scripts/review_schema_comments.py approve --id N --edit "说明"

# 4. 或在前端"表与注释"页补充字段注释(写 override 层)

# 5. 生成演示数据(可选)
uv run python scripts/seed_data.py --count 1000

# 6. 启动
powershell -File scripts/dev.ps1 restart
```

> 模型名注意:DeepSeek 只认小写 `deepseek-v4-pro` / `deepseek-v4-flash`(大写会 400);
> 主模型负责计划/解释,SQL 生成可用千问等专门模型。
