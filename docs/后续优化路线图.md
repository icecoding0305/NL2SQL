# NL2SQL 后续优化路线图

状态：迭代一已完成，迭代二进行中  
最近更新：2026-08-25

## 迭代一实施结果（2026-08-21）

- 已新增高置信简单查询的确定性 QueryPlan，按完整 Schema Grounding 判断是否可编译，
  不再使用关键词复杂度分类。
- 当前确定性覆盖单表筛选、聚合、分组、HAVING、排序、Top-N，以及唯一可信关系的一跳 JOIN。
- OR/NOT、EXISTS、时间、窗口、多事实或低置信绑定仍自动回退计划模型。
- 已增加 QueryPlan 到 SQL AST 的结构覆盖校验，检查 WHERE、HAVING、GROUP BY、
  ORDER BY 方向和 LIMIT，防止 SQL 翻译遗漏用户要求。
- 第一次低置信 Schema 召回会自动生成业务语义改写并重新召回；第二次仍低置信时
  带警告进入严格计划校验，不再要求用户选择物理表。
- 字段召回增加最小表覆盖约束：一张明细表可完整承载查询时，优先收敛到该表，
  避免因列级分数微小差异引入不必要的多表 JOIN。
- 值域校准被限制在已确定的 Schema 子图内，样本值不能再把筛选条件迁移到计划外表。
- 真正的业务口径歧义仍可澄清，但普通用户不会看到物理表名和字段名。
- 本迭代 60 项定向回归通过，覆盖确定性计划、输出契约、语义契约和召回路由。

## 一、当前基线

- 代表性查询端到端耗时已由约 161 秒降低至 4.35 秒。
- 单次查询的模型调用已由 5 次降低至 1 次，主要耗时为 QueryPlan 生成，约 2.8 秒。
- 当前主链路为 `用户问题 → SemanticGraph → QueryPlan → LogicalPlan → SQL`。
- 已有原问题、SemanticGraph、QueryPlan 三层语义覆盖校验。
- 已支持常规筛选、聚合、HAVING、排序、TopN 和多事实表预聚合。
- 已使用 Query M-Schema 限制模型上下文，并持久化向量缓存。

## 迭代二阶段一实施结果（Schema 安全画像，2026-08-21）

- Schema 导入改为按价值选择采样字段，每张变化表默认最多选择 20 列、读取 100 行。
- 敏感字段、凭据字段、BLOB、二进制、大文本、JSON 和空间字段默认不进入采样 SQL。
- 缺注释表的描述生成复用同一次字段画像，不再额外执行第二次数据样本查询。
- M-Schema 记录 `profiling_policy` 和字段 `profile_status`；画像策略变化时，下一次增量同步会自动重新画像。
- 字段向量文本只允许写入非敏感、低基数枚举样例；普通文本、编码和敏感样例只保留在服务端或被抑制。
- Schema 同步结果增加画像表数、字段数、样本行数和跳过字段数，便于前端展示导入成本。
- 本阶段 24 项定向测试通过，覆盖选择性采样、增量策略变更、向量样例边界和值绑定兼容性。

## 迭代二阶段二实施结果（关系发现与 SQL 候选提炼，2026-08-24）

- Schema 同步会根据同名关联字段、类型兼容性、主键/唯一键、索引和安全样本覆盖率生成候选关系。
- 自动关系采用 `candidate / inferred / verified / rejected` 状态治理；只有 `verified / confirmed` 且启用的关系能进入运行时 JOIN 图。
- 表关系页面展示候选置信度和发现证据，并提供“确认使用”和“拒绝”入口；被拒绝关系不会在下次同步时自动恢复。
- 模型 SQL 路径首轮默认生成两个候选，通过 SQL AST、目标表和 QueryPlan 结构覆盖进行本地评分选择，不增加选择模型调用。
- 首选 SQL 校验或执行失败时，优先尝试已经生成的备用候选；候选耗尽后才携带失败证据调用模型 Refiner。
- 确定性简单 SQL 仍只生成一个候选，不增加模型耗时。
- 本阶段 38 项相关后端测试与前端生产构建通过。

## 迭代二阶段三实施结果（联合 Schema Linking，2026-08-25）

- 字段选择由“每个语义槽位独立取最高分”升级为有界联合组合搜索，同时评价所有度量、
  过滤、属性和分组字段。
- 联合评分优先复用同一事实表；确需多表时只认可 M-Schema 或关系管理中可用的关系路径，
  并对新增表、Join 跳数和不连通组合施加成本。
- 关系一致性只作为高质量候选之间的决胜条件：候选必须先达到相对语义阈值，不能因为
  与主表相连就把弱相关字段提升为有效字段。
- SchemaPlan、输出字段绑定和后续 Query M-Schema 共享同一组物理字段偏好；当计划内存在
  语义足够接近的字段时，不再从无关表重新选择同名字段。
- 保留“地址”等明确宽泛结果的一对多展开；普通输出维持一个语义输出对应一个主物理绑定。
- 代表性回归覆盖“贷款金额 + 产品”场景：即使其他分析表的 `prd_code` 单字段分数略高，
  仍选择可在 `dws_ar_loan_info` 单表完成的产品字段和贷款金额字段。
- 本阶段定向测试 24 项通过；扩展检索套件另有 7 项失败，涉及术语扩展、候选差距、
  旧关系状态和时间澄清，均未修改其实现，本阶段不将其计入验收结果。

## 迭代二阶段四实施结果（分层 Query M-Schema，2026-08-25）

### 第一阶段：完整性与上下文预算

- Query M-Schema 从“每表固定 16/24 列”改为可配置的全局表数、总字段数和备用字段预算。
- 用户输出、语义绑定、过滤字段、关系键、粒度键和必要身份键属于必需字段，不因预算被裁剪；
  只有近分备用字段可以被淘汰。
- 模型调用前增加 Query M-Schema 契约校验，覆盖必需输出绑定、语义绑定、关系字段、
  QueryPlan 标识符和多表连通性；上下文仍不完整时停止生成，禁止模型猜测字段或 JOIN。
- 新增 `execution` Profile。SQL 生成只接收已验证 QueryPlan 实际引用的表、字段和关系，
  不再重新构建可能过窄的 Precision Schema。
- 提示词上下文移除与 SemanticGraph 重复的完整 QueryIntent，只保留查询类型摘要。

### 第二阶段：受控 Recall 与粒度风险

- Recall 默认只增加计划内的高分备用字段；只有字段覆盖、输出、分组、排序或关系路径类错误
  才允许扩大 Schema 子图。
- 扩表严格限制为可信关系连接的一跳候选表，并受总表数预算限制；未验证关系和不连通表
  不会进入模型提示词。
- Query M-Schema 保留关系基数；实体粒度的一对多普通 JOIN、聚合粒度的多对多普通 JOIN
  会产生行数放大或重复累计风险，交由计划校验拦截。

### 第三阶段：监控与审计

- Precision、Recall、Execution 分别记录表数、字段数、必需/备用字段数、预算上限、
  预算超限、扩展原因、扩展表数、契约错误数、字符数和估算 Token 数。
- 指标随三类 Query M-Schema 写入查询审计；新增 `query_mschema_execution` 持久化字段。
- 监控指标不会进入模型提示词，避免增加 Token 或让模型误把诊断信息当成 Schema 事实。
- 定向回归覆盖全局预算、必需字段保护、可信一跳扩表、不连通表排除、Execution 精确字段、
  必需输出缺失和多对多聚合风险。
- 联合 Schema Linking 与分层 Query M-Schema 相关的 50 项定向回归全部通过。

## 三、推荐实施顺序

### P1：复杂查询正确性

1. 增加 `EXISTS / NOT EXISTS` 的强类型语义结构。
2. 扩展窗口函数、排名、累计值、同比和环比计划结构。
3. 增加时间范围、时间粒度和时间口径表达。
4. 扩展确定性 SQL 编译器并补充本次修改范围内的测试。

验收标准：

- 用户明确要求的输出、条件、存在性、分组、排序和时间口径全部进入 QueryPlan 与 SQL。
- 存在性条件不再依赖普通 JOIN 和 DISTINCT 模拟。
- 多事实表连接不会造成金额或数量重复累计。
- 不支持的复杂结构明确失败，不生成语义不完整的 SQL。

### P2：计划生成性能

1. 实现已验证 QueryPlan 缓存。
2. 缓存键至少包含 `database_id`、M-Schema `semantic_hash`、规范化问题、有效会话上下文和模型配置签名。
3. 为单表、明确字段、简单过滤和简单聚合实现确定性 QueryPlan。
4. 低置信度或复杂问题自动回退计划模型。

验收标准：

- 缓存不得跨数据库、跨 Schema 版本或跨权限范围复用。
- 重复查询缓存命中时不调用计划模型。
- 高置信简单查询不调用计划模型。
- 缓存命中查询的目标响应时间约为 1 秒。

### P3：Schema 召回与关系治理

1. 按主体、输出字段、过滤字段和关系路径进行分层召回。（已完成第一阶段）
2. 使用联合候选评分先确定主事实表和最小连通字段组合，再补充维度表和桥接表。（已完成第一阶段）
3. 根据字段名、类型、唯一性、覆盖率和数据抽样生成候选关系。
4. 使用 `candidate → inferred → confirmed` 管理关系可信度。
5. SQL 只能自动采用通过阈值的数据验证关系或人工确认关系。
6. 为表补充明细粒度、唯一键和基数信息，并在联合评分中惩罚可能造成重复聚合的 Join。
7. 仅在候选近分或子图不稳定时启用轻量重排器，输入限定为 Top-N 字段和候选子图，
   不传完整 Schema。

验收标准：

- 主表 Recall@K、字段 Recall@K 和 Join 路径正确率有可重复的评测结果。
- 增加槽位绑定准确率、最小表覆盖率、连通子图召回率和聚合粒度正确率。
- 未验证关系不会静默进入生产 SQL。
- Schema 更新后只重建发生变化的向量文档。

### P4：交互与运营闭环

1. SQL 执行结果优先返回，智能总结异步补充或由用户按需触发。
2. 前端合并内部节点，只展示理解、规划、执行和结果阶段。
3. 保存语义覆盖失败、计划失败、SQL 校验失败、执行失败和用户反馈。
4. 失败样本经脱敏和审核后进入离线回归集。

验收标准：

- 结果总结不阻塞结果表格展示。
- 每类失败都有明确分类和可定位 trace。
- 线上失败样本不会未经审核直接形成业务规则。
- 持续统计 SQL Execution Accuracy、P50/P95 响应时间、缓存命中率和用户重新提问率。

## 四、实施原则

- 正确性优先于减少模型调用。
- 模型负责语义判断，强类型结构和确定性节点负责约束、校验与执行。
- 不向任何模型提示词传入完整数据库 Schema，只传 Query M-Schema。
- 不在缺少关系事实时猜测 JOIN。
- 所有缓存必须绑定数据库、Schema 版本、权限范围和模型配置。
- 每个阶段只测试本次修改涉及的功能，并保留代表性端到端回归用例。
