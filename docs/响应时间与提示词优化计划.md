# 响应时间与提示词优化计划

状态：P0 已实施，P1 部分实施  
记录日期：2026-08-19

## 一、基线证据

代表问题：`统计户籍地址为上海的客户的逾期情况`

最近一次慢查询 `t1787108945485` 总耗时约 161 秒：

| 节点 | 耗时 | 结论 |
| --- | ---: | --- |
| query_resolution | 138.76 秒 | 主要瓶颈 |
| schema_retrieval | 4.29 秒 | 包含宽泛字段具体化模型调用 |
| plan_generation | 2.68 秒 | 当前可接受 |
| sandbox_execution | 0.62 秒 | 数据库不是瓶颈 |
| result_interpretation | 14.10 秒 | 第二大可消除耗时 |

`query_resolution` 第一次模型调用耗时 121.29 秒，返回的 `assumptions` 等嵌套字段不符合
Pydantic 结构；内部重试又耗时 17.46 秒。结果总结随后再次调用模型，耗时 14.10 秒。

## 二、性能优化顺序

### 实施结果（2026-08-19）

同一代表问题优化后端到端耗时 4.35 秒，成功返回 16 行，与优化前 SQL 语义一致：

| 节点 | 优化前 | 优化后 |
| --- | ---: | ---: |
| query_resolution | 138.76 秒 | 6.8 毫秒 |
| schema_retrieval | 4.29 秒 | 39.78 毫秒 |
| plan_generation | 2.68 秒 | 2.80 秒 |
| sandbox_execution | 0.62 秒 | 0.61 秒 |
| result_interpretation | 14.10 秒 | 0.55 毫秒 |

模型调用从 5 次降为 1 次，仅保留必要的 QueryPlan 生成。已完成：按需问题理解、节点级超时、
SDK 隐式重试关闭、问题理解零重试、常见 assumption 结构兼容、唯一主题字段规则化、
多行分组确定性总结、result thinking 关闭，以及 SQL fallback 上下文精简。

### P0：已实施

1. 将 `clarification_rules.yaml` 的 `query_resolution.use_llm` 从 `always` 改为 `auto`。
2. 问题理解内部结构化重试从 1 次改为 0 次；失败直接使用确定性语义解析。
3. 为模型客户端增加配置化请求超时和 `sdk_max_retries=0`：
   - query_resolution：8 秒；
   - projection_resolution：8 秒；
   - plan_generation：20 秒；
   - result_interpretation：6 秒。
4. `result_summary_mode=auto` 时，多行分组结果使用确定性总结；只为确有价值的单行全局聚合调用模型。
5. 为 result_interpretation 禁用 thinking，并将输出预算限制在约 800 Token。

预期：该代表问题从约 161 秒下降到约 8～15 秒。

### P1：部分实施

1. 宽泛主题只有一个高置信直接相关字段时，规则直接生成 ProjectionDecision。（已完成）
2. 多个近义候选或组合主题才调用 projection_resolution 模型。
3. 多行分组结果已改为确定性总结；智能总结异步增强仍待实施。
4. SemanticGraph、ProjectionDecision、SchemaPlan 和已验证 QueryPlan 分层缓存仍待实施。

### P2：稳定性与可观测性

1. 设置查询总时间预算，超时优先降级可选模型节点。
2. 审计中展示模型首 Token 时间、完整响应时间、结构校验状态和降级原因。
3. 按数据库 `semantic_hash`、模型配置签名和会话上下文构造缓存键。

## 三、提示词审查结论

### 1. query_resolution

主要问题：

- 当前配置强制每个问题调用模型，与已有确定性解析和 Schema 后置具体化重复。
- DeepSeek 不走 function calling；纯 JSON 首次请求只提示顶层必填字段，没有提供完整嵌套 JSON Schema。
- 提示词没有给出 `QueryAssumption`、`SemanticPredicate` 等关键嵌套对象的紧凑示例，容易产生
  `assumption` 代替 `content`、字符串代替对象等结构错误。
- 校验失败后，客户端把上一轮输出、完整错误和完整 JSON Schema 全部追加到第二次请求，提示词显著膨胀。

建议：

- 默认 `use_llm=auto`；确定性解析高置信时跳过模型。
- 添加一个紧凑且完整的 ResolvedQuery 示例，明确 assumptions 的 `content/source/materiality`。
- 明确“字段选择、指标候选、表关系”等 Schema 可解决内容不得写入 unresolved slots。
- 对字符串 assumption 和 `assumption` 别名做输入规范化，避免只因格式差异重试。
- query_resolution 不做内部模型重试。

### 2. projection_resolution

主要问题：

- “选择 3 至 8 个字段”与主题只有一个真实相关指标的场景冲突，可能诱导凑数。
- 基本信息展开与主题指标具体化使用同一数量规则，职责不够清晰。

建议：

- 改为“选择 1 至 8 个，绝不为满足数量凑字段”。
- 基本信息建议 3～8 个可读字段；主题指标只选直接相关字段，通常 1～4 个。
- 唯一高置信候选走规则，不调用模型。

### 3. plan_generation

主要问题：

- 多条规则重复声明 Query M-Schema 是唯一 Schema、禁止完整 Schema、字段只能来自绑定。
- 提示词同时要求模型完成业务规划、物理绑定、ID 记账和结构规范化；部分工作已经由
  `plan_normalizer.py` 确定性完成。
- 示例和规则较长，增加输入 Token，也提高模型遗漏后半部分约束的概率。

建议：

- 按优先级压缩为：绑定事实 > 关系事实 > 语义契约 > 输出格式。
- OutputBindings、SemanticBindings 已确定的内容由代码重建，模型只决定关系算子结构。
- 删除重复的完整 Schema 禁令和重复字段来源约束，保留一处强约束。
- 保留 WHERE/HAVING、粒度、多事实预聚合和 not_exists 等真正需要模型理解的规则。
- 将输出示例缩减为普通查询和聚合查询两个最小示例，按查询类型只注入一个。

### 4. result_summary

主要问题：

- auto 模式下所有分组查询均调用模型，即使确定性摘要已经足够。
- 当前节点未显式禁用 thinking，少量可见文字也可能消耗较多推理 Token。
- “1～5 条发现”会诱导模型在信息不足时生成冗长内容。

建议：

- 多行分组结果默认确定性总结；智能总结异步或用户按需触发。
- 禁用 thinking，限制为最多 3 条发现、2 条必要说明和约 250 个中文字符。
- 明确没有显著差异时不生成“发现”占位内容。

### 5. SQL fallback

主要问题：

- `sql_from_plan` 的任务是机械翻译已验证计划，但仍注入用户问题、会话、术语和较多 Schema 语义，
  存在重新解释业务含义的风险，也增加上下文。
- `sql_from_query` 与“所有查询统一生成计划”的当前架构不一致，应仅保留旧状态兼容用途。

建议：

- `sql_from_plan` 只传方言、QueryPlan、最小 Query M-Schema 和重试错误。
- 不再传会话历史和术语原文；这些内容已经固化在已验证 QueryPlan 中。
- 对 `sql_from_query` 标记 legacy，仅在历史 checkpoint 恢复时使用。

## 四、验收指标

- 代表问题端到端 P50 ≤ 10 秒，P95 ≤ 30 秒；
- query_resolution 模型调用率显著下降；
- 结构化输出重试率 < 5%；
- 多行分组结果默认不产生同步总结模型调用；
- SQL Execution Accuracy、字段召回率和 Join 路径正确率不得下降；
- 任何降级都必须保留语义覆盖、字段存在性与关系事实校验。
